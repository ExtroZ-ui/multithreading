## 1. Цель работы

Цель работы — изучить средства Java для организации корректного взаимодействия потоков без использования тяжёлой блокировки во всех случаях:

- `volatile` — для обеспечения видимости изменений между потоками;
- `AtomicInteger` — для атомарного изменения целочисленного значения;

## 2. Безопасная остановка потока с volatile

Для управления завершением рабочего потока создан класс `VolatileStopExample`.

В нём используется поле:

```java
private volatile boolean stopRequested;
```

Рабочий поток выполняет цикл до тех пор, пока `stopRequested == false`.

Главный поток через некоторое время вызывает метод:

```java
requestStop();
```

который устанавливает значение `true`.

### Почему используется volatile

Если убрать `volatile`, Java не гарантирует, что один поток немедленно увидит изменение поля, выполненное другим потоком. JVM и процессор могут использовать кэширование и оптимизации.

`volatile` обеспечивает:

1. видимость последнего записанного значения между потоками;
2. запрет некоторых опасных перестановок операций относительно volatile-чтения и volatile-записи.

### Пример результата

```text
[volatile] Рабочий поток запущен.
[volatile] Запрошена остановка.
[volatile] Рабочий поток остановлен.
```

Важно: `volatile` не делает составные операции атомарными. Например, операция `counter++` по-прежнему состоит из чтения, изменения и записи.

## 3. Потокобезопасный счётчик через AtomicInteger

Создан класс `AtomicCounter`.

Поле счётчика:

```java
private final AtomicInteger value = new AtomicInteger(0);
```

Метод увеличения:

```java
public int increment() {
    return value.incrementAndGet();
}
```

Метод получения текущего значения:

```java
public int get() {
    return value.get();
}
```

Для проверки запускается несколько потоков. Каждый поток выполняет большое количество инкрементов.

Например:

- 8 потоков;
- по 100 000 инкрементов;
- ожидаемое значение — 800 000.

При использовании `AtomicInteger` итоговое значение всегда совпадает с ожидаемым.

### Почему AtomicInteger потокобезопасен

`AtomicInteger` использует атомарные операции уровня JVM/процессора, обычно основанные на CAS — Compare-And-Set.

CAS логически выполняет проверку:

```text
если текущее значение всё ещё равно ожидаемому,
то заменить его новым значением
```

В отличие от `synchronized`, при обычной конкуренции поток не обязан захватывать монитор объекта.

## 4. Singleton-кэш через AtomicReference

Создан класс `AtomicSingletonCache`.

Кэш хранит один объект типа `String`.

Поле:

```java
private final AtomicReference<String> cache = new AtomicReference<>();
```

При обращении к `getOrCreate()` выполняется:

1. чтение текущего значения;
2. если значение уже существует — оно возвращается;
3. если значение `null` — создаётся кандидат;
4. выполняется `compareAndSet(null, candidate)`;
5. поток, который первым успешно выполнил CAS, сохраняет объект;
6. остальные потоки получают уже опубликованное значение.

Ключевой участок:

```java
if (cache.compareAndSet(null, candidate)) {
    return candidate;
}
return cache.get();
```

Таким образом, в кэше в итоге хранится один экземпляр значения, даже если несколько потоков одновременно пытались его создать.

### Возможная особенность

При такой lock-free реализации два потока теоретически могут одновременно создать временные объекты-кандидаты, но только один из них будет опубликован в `AtomicReference`.

Для дешёвого создания объекта это нормальная цена за отсутствие блокировок.

## 5. Нагрузочное тестирование

В классе `PerformanceTest` выполняются три группы тестов:

1. многократное чтение `volatile`-флага;
2. конкурентные инкременты `AtomicInteger`;
3. конкурентный доступ к `AtomicReference`-кэшу.

Для измерения времени используется:

```java
System.nanoTime()
```

Результаты зависят от:

- процессора;
- количества физических и логических ядер;
- версии JVM;
- фоновой нагрузки;
- режима энергопотребления ОС.

Пример результата:

```text
[perf] volatile-read test: 25 ms
[perf] AtomicInteger test: 140 ms
[perf] AtomicReference cache test: 18 ms
```

Эти числа не являются универсальными и приведены только как пример формата.

### Оценка производительности

`volatile` обычно дешевле полной синхронизации, когда требуется только публикация состояния или простой флаг.

`AtomicInteger` хорошо подходит для счётчиков при умеренной конкуренции. При очень высокой конкуренции все потоки обновляют одну и ту же область памяти, поэтому производительность может снижаться.

`AtomicReference` подходит для lock-free алгоритмов и атомарной публикации объектов.

## 6. Корректные ситуации

### Корректная остановка

```java
private volatile boolean stopRequested;
```

Поток гарантированно увидит запрос остановки.

### Корректный инкремент

```java
AtomicInteger counter = new AtomicInteger();
counter.incrementAndGet();
```

Инкремент атомарен.

### Корректное обновление ссылки

```java
reference.compareAndSet(null, newValue);
```

Только один конкурентный поток сможет выполнить замену при ожидаемом значении `null`.

## 7. Некорректные ситуации

### Обычный boolean без volatile

```java
private boolean stopRequested;
```

Один поток изменяет флаг, другой читает его в цикле.

Такой код содержит проблему видимости. По модели памяти Java нет гарантии своевременного обнаружения изменения.

### Небезопасный счётчик

```java
private int value;

public void increment() {
    value++;
}
```

Операция `value++` не атомарна.

Фактически она включает:

1. чтение `value`;
2. прибавление единицы;
3. запись обратно.

Два потока могут прочитать одно и то же старое значение и затем записать одинаковый результат. Один инкремент будет потерян.

В проект включён `UnsafeCounter`, который демонстрирует эту проблему.

Например, ожидалось:

```text
800000
```

а фактически при некоторых запусках может получиться:

```text
673421
```

Точное значение зависит от планирования потоков и может отличаться при каждом запуске.

## 8. Вывод

В ходе работы были рассмотрены три важных инструмента многопоточного программирования Java.

`volatile` следует использовать, когда нужно обеспечить видимость изменений между потоками и операция не требует составного атомарного изменения.

`AtomicInteger` подходит для потокобезопасных счётчиков и других атомарных операций с целыми числами.

`AtomicReference` позволяет атомарно обновлять ссылки и строить lock-free алгоритмы, например singleton-кэш.

Atomic-классы часто позволяют избежать явного `synchronized`, но не устраняют необходимость правильно проектировать алгоритм. Особенно важно понимать разницу между видимостью и атомарностью.

Итог: `volatile` решает задачу видимости, а `Atomic*` решают задачи атомарного конкурентного изменения состояния.
